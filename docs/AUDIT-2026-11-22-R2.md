## 0. 一句话结论

R1 修掉的是"工具层能被单个输入打崩"这类**点状缺陷**，R2 暴露的是**面状缺陷**：

1. **配置把系统放进了一条必然触发的死亡链**——`soft(600k) > window(300k)`，router 会在折叠之前撞满窗口 → 400 → 事件不 ACK → 重放时再追加一条同内容 digest → 更快超限 → 5 次后 supervisor 永久放弃。**这不是概率问题，是上下文长到某个点就一定发生。**
2. **命令规则的"写"分支只认 8 个命令名**，`copy / xcopy / robocopy / curl -o` 完全不在判定范围内；`-Path:` 粘连、`\\?\` 前缀、管道包裹各自有独立缺口。实测 17 条越权命令中 **12 条返回 PASS（零判定）**。
3. **一个进程内线程的死亡没有任何人知道**——outbox 发送线程的 `try` 只包住 Redis 读取，单条消息处理抛异常就终结整个线程，进程、飞书长连接、心跳全部看起来正常。

## 2. P0：严重

### P0-1 配置矛盾把 router 推进"必然 400 → 永久停摆"的死亡链

**配置事实**（`.env:25-26` + `config.py:149`）：

```
context_window_tokens = 300_000      # 没被 .env 覆盖，用默认值
CONTEXT_SOFT_TOKENS  = 600_000       # = 窗口的 200%
CONTEXT_HARD_TOKENS  = 800_000       # = 窗口的 266%
```

**代码事实**：`agents/router/graph.py:72` 只挂 `ContextBudgetMiddleware`，router **没有** `CompactMiddleware`；折叠触发条件是"估算 token 超过 soft"，即 600k。

于是：上下文增长到 300k（模型窗口上限）时，折叠还差 300k 才触发。若 `deepseek-v4.1-flash` 的有效窗口确实是 300k，**router 一定先拿到 400，而不是先折叠**。

**死亡链**（每一步都有代码依据）：

| 步 | 位置 | 行为 |
|---|---|---|
| 1 | `main_router.py:570` | 每批事件把 `digest` 作为**新 HumanMessage 追加**到同一个 `router_thread_id` |
| 2 | `main_router.py:775-777` | 400 抛到 `main()` → `exit_code=2`，**不 ACK** |
| 3 | `main_gateway.py:287-296` | supervisor 计一次失败、退避重拉 |
| 4 | `bus/stream.py` XAUTOCLAIM | 同一批事件被重新认领 |
| 5 | 回到步 1 | 同一 thread 再追加一条**完全相同**的 digest，上下文只增不减 |
| 6 | `main_gateway.py:299-301` | `_failures >= 5` → `return`，**永久不再拉起 router** |

第 6 步之后：所有新消息、定时、worker 回报全部堆在 stream 里，`/api/status` 显示"待机"，用户视角是"机器人突然不说话了"，只有重启 gateway 能恢复。

**为什么比 R1 的 P0-4 更严重**：R1 把它描述为"毒消息"（概率事件），但 `soft > window` 让**凡是让上下文长到窗口上限的对话都会走到这里**，包括一次正常的长任务。

**修复顺序**（三步都要，缺一不可）：
1. 先修配置：`CONTEXT_WINDOW_TOKENS` 写进 `.env` 并等于模型真实窗口；`CONTEXT_SOFT_TOKENS` 设成窗口的 65%，`HARD` 设成 85%。这本来就是 `config.py:147` 注释说的"按比例计算"，被 `.env` 的绝对值覆盖破坏了。
2. 给 router 挂 `CompactMiddleware`（worker 侧已有，`agents/worker/graph.py:55`）。
3. 把"批处理异常"限制在 batch 内：捕获 `GraphRecursionError` / API 4xx，写一条 `ok=false` 的 turn 后 **ACK**，并给用户发一条降级提示。不要让单批异常杀掉整个进程。

### P0-2 Grep 经 NTFS junction 读出工作区外的文件（已实测）

**位置**：`tools/fs.py:846-862`

```python
        if target.is_file():
            files = [target]
        else:
            files = _walk_files(target)          # ← 无 is_within 兜底
        ...
        for file_path in files:
            if has_excluded_part(file_path, base_root):   # 只排除 .git 等目录名
                continue
```

`_walk_files`（`tools/fs.py:254-259`）用 `os.walk`，而 `os.walk` **跟随 junction**（`Path.is_symlink()` 对 junction 返回 False，所以任何"是不是链接"的检查都判不出来）。

**根因还有一层**：`tools/paths.py:31` 的 `is_within` 注释明写"**不解析符号链接**"，只用 `abspath + normcase`。所以即使给 Grep 补一句 `is_within(item, base_root)`，**也拦不住 junction**——必须 `item.resolve()` 之后再比。

**实测**（`D:/tmp/probe_ws` 里建 `mklink /J link_out D:\tmp\probe_outside`，非管理员即可建）：

```
_walk_files 遍历结果含 secret: ['D:\\tmp\\probe_ws\\link_out\\secret.txt']
对 secret 的 is_within（经 link）: True          ← 兜底也失效
```

对照：`Read` 走 `resolve_in_roots`（内部 `candidate.resolve()` + `is_within`）→ 正确拒绝；`Glob` 上一轮已补 `resolve()` → 正确拒绝。**Grep 是三个文件工具里唯一敞口的。**

**影响**：工作区里只要有一个指向盘符/家目录的联接（Windows 上很常见），就能读任意文本文件；配合 `Grep` 的正则可做内容检索，不只是枚举文件名。

**修复**：
1. `_walk_files` 里对 `dirnames` 剪枝：`os.lstat(p).st_reparse_tag == IO_REPARSE_TAG_MOUNT_POINT` 的目录不进入；
2. 每个 `file_path` 处理前加 `if not is_within(file_path.resolve(), base_root): continue`；
3. 顺带修 `is_within` 的语义坑：调用方想要"物理越界"时一律先 `resolve()`。

### P0-4 `\\?\` verbatim 前缀让整个路径禁区失效（已实测）

**位置**：`tools/rules.py:62-66`（`_resolved`）→ `_is_under`（`tools/rules.py:408-413`）

**实测**：

|---|---|

### P0-6 outbox 发送线程可被单条消息打死，无人重启（代码确认）

**位置**：`main_gateway.py:199-221`

```python
        while not self._stop_event.is_set():
            try:
                result = self._reader.xreadgroup(...)      # try 只包住读取
            except Exception:
                logger.warning("outbox 读取失败", exc_info=True)
                self._stop_event.wait(1.0)
                continue
            ...
            for entry_id, fields in result[0][1]:
                self._handle(entry_id, normalized)          # ← 无保护，抛异常直接终结线程
```

`_handle` 里包含 `feishu send_text`（网络）、`redis.get/set/xack`、`event_from_redis` 解析。任一抛异常 → `run()` 退出 → daemon 线程消失。而：

- `run_forever` 不检查线程存活；
- `gateway.ps1` 只按进程判活；
- 飞书长连接、心跳线程都照常运行。

**结果**：进程"活着"、能收消息、能在 router 里生成回复、能写 outbox，但**没有任何外发**。用户在飞书里发消息永远没回应，日志只有一行 traceback。这比 P0-1 更难发现，因为它看起来一切正常。

**叠加 R1 的 P0-3（无 XAUTOCLAIM）**：线程死前已从 PEL 取出的那条回复，之后永远不会被重投；ReplyUser 的幂等键停在 `"pending"`，即使 router 重放也会被判"已发送"。

**修复**：
1. `try/except` 把 `_handle` 一起包住，失败记 `send_failures` 并在同一 entry 上有限重试（3 次后 ack 到死信 + 写 `system/send_failed`）；
2. 启动时跑一次 `XAUTOCLAIM(idle>60s)` 捞回 PEL；
3. `run_forever` 每分钟检查 `sender.is_alive()`，死了就重建线程并告警。
